# 이비인후과 홈페이지 구축 계획

작성일: 2026-09-24 · 상태: 사용자 답변 반영 완료 · 구현 전 기획안 · 구현 담당: Sol

확정 정보: **알지 이비인후과 / 신매역 / 네이버 예약 / Anthropic 홈페이지를 참고한 현대적인 디자인**. 사진·프로필 등 준비된 자료는 없으며 개원 일정과 운영 담당은 미정이다. 법정 의료기관 표기와 상세 주소는 추후 확인한다.

## 1. 목표와 기본 방향

방문자가 첫 화면에서 어떤 진료를 하는지, 언제 방문할 수 있는지, 어떻게 예약하는지 파악하게 한다. 진료를 찾아본 뒤 의료진을 확인하고 예약 또는 길찾기로 이어지는 흐름을 만든다.

- 주 방문자: 만성·알레르기 비염으로 불편한 사람, 난청·이명으로 진료를 찾는 사람, 머리·목 부위의 암과 종양으로 상담을 원하는 사람. 구체적인 검사·치료 범위는 추후 확인한다.
- 브랜드 방향: 가까운 곳에서 충분한 설명을 들을 수 있는 차분하고 친근한 의원.
- 문구 가안: “귀·코·목의 불편함, 충분히 듣고 설명하겠습니다.” 실제 진료철학에 맞춰 확정한다.
- 중점 진료: ① 만성 비염·알레르기 비염 ② 난청·이명 ③ **암**. 환자에게 암을 먼저 보여주고, 설명에 머리·목 부위의 암과 종양(두경부 종양)을 병기한다. 암 치료·수술·항암 또는 상급병원 연계 제공을 임의로 가정하지 않는다.
- ‘대학병원급’, 보유 여부가 확인되지 않은 검사장비, 임의의 경력·성과 수치는 사용하지 않는다.

## 2. 디자인 방향

사용자가 지정한 [Anthropic 홈페이지](https://www.anthropic.com/)를 디자인 참고로 삼는다. 이 프로젝트에는 **따뜻한 아이보리 배경, 짙은 먹색 타이포그래피, 넓은 여백, 큰 제목, 얇은 구분선, 절제된 그래픽**을 제안한다. 참고 사이트의 로고·카피·독점 소재를 복제하지 않고 알지 이비인후과의 독자적인 화면으로 구성한다.

색상 후보는 배경 `#F5F2EA`, 본문 `#24231F`, 보조 배경 `#E9E5DB`, 제한적인 테라코타 강조 `#B96B50`이다. 이는 알지 홈페이지용 제안값이며 Anthropic의 정확한 색상을 추출한 값은 아니다. 본문·버튼 조합은 구현 시 대비를 확인한다. 기존 네이비·청록 가안은 대체한다.

- 한글 본문은 읽기 쉬운 산세리프 16~18px. 큰 제목은 한글 명조 또는 개성 있는 한글 서체를 소량 사용하고, 모바일 줄바꿈을 확인한다. 제목용 서체의 라이선스와 로딩 성능을 검토한다.
- 한 화면에 주 행동 버튼 1개를 강조하고 전화·길찾기는 보조 행동으로 둔다.
- 초기 메인은 사진 없이 완성 가능한 타이포그래피와 추상적인 선·면 그래픽으로 구성한다. 호흡과 소리를 연상시키는 형태를 절제해 사용한다. 프로필·장비·시설은 실제 자료 확보 후 추가한다.
- 핵심 기능은 머리·목 그림의 귀·코·입·목을 클릭하는 진료 탐색이다. 텍스트 버튼도 함께 제공한다. 상세 동작은 `interaction-and-screen-spec.md`를 따른다.
- 해부 일러스트는 진료 상세에서 설명에 필요한 만큼 사용한다.
- 데스크톱 본문 최대 폭 약 1200px, 모바일 360px부터 대응. 중점 진료는 큰 번호와 제목, 짧은 설명을 가진 넓은 가로 행으로 구성한다. 반복되는 카드와 그림자보다 구분선·색면으로 정보 위계를 만든다.
- 자동재생 영상과 진입 팝업은 초기 구성에서 제외한다. 휴진 안내는 공지 띠로 보여준다.

## 3. 메뉴와 페이지

상단 메뉴는 **병원소개 / 진료안내 / 검사안내 / 이용안내 / 소식**으로 묶는다. 예약 버튼은 별도 배치한다. ‘중점 진료’는 진료안내 안에 두고 메인에서 강조해 메뉴 중복을 줄인다.

| 경로 | 내용 | 초기 범위 |
| --- | --- | --- |
| `/` | 진료 탐색, 의원 소개, 방문 정보 요약 | 필수 |
| `/about` | 진료철학, 의료진, 시설 | 필수 |
| `/care` | 제공 진료 분야 전체 | 필수 |
| `/care/[slug]` | 비염·알레르기, 난청·이명, 암(두경부 종양) | 공통 상세 템플릿 |
| `/examinations` | 실제 제공 검사, 과정·준비사항 | 필수 |
| `/visit` | 진료시간, 휴진, 주소, 교통·주차, 예약 방법 | 필수 |
| `/faq` | 예약·방문·검사 관련 질문 | 필수 |
| `/notices`, `/notices/[slug]` | 휴진·운영 변경 공지 | 필수 |
| `/health`, `/health/[slug]` | 의료진이 검토한 건강정보 | 템플릿 구축, 승인된 글부터 공개 |
| `/fees` | 비급여 항목·금액·검색·분류 | 필수 |
| `/privacy` | 실제 운영 방식에 맞는 개인정보처리방침 | 공개 전 확정 |
| `/credits` | 사용 소재 출처·라이선스 | 해당 소재 사용 시 |

중점 진료는 해당 `/care/[slug]`로 연결한다. 추가 질환별 페이지는 콘텐츠가 준비되면 확장한다. 모든 분야와 장비를 처음부터 제공한다고 가정하지 않는다.

주 행동은 **네이버 예약**으로 통일한다. 모바일 하단도 예약을 중심으로 구성하고 전화·길찾기는 실제 정보 확보 후 보조로 추가한다. 예약 URL이 없는 시안에는 미연결 상태를 명확히 표현한다. 카카오채널은 초기 범위에서 제외한다. 의료진·장비·시설·운영시간 등 미제공 콘텐츠는 빈 섹션으로 길게 나열하지 않고 시안에서 생략하며, 데이터와 페이지 틀만 준비한다.

## 5. 기능 및 운영 기준

### 초기 구현

- 외부 네이버 예약을 기본으로 연결. 전화와 지도 길찾기는 실제 정보 확보 후 추가.
- 클릭·터치·키보드로 사용하는 인체 탐색과 결과 패널, 진료 상세 3개 연결.
- 모바일 메뉴, 키보드로 사용할 수 있는 FAQ, 진료 분야 상세 이동.
- 비급여 검색: 항목명·코드 검색, 분류 필터, 결과 없음 안내, 금액·변경일 직접 표시.
- 공지와 건강정보는 별도 콘텐츠 파일로 관리한다. 수정 후 빌드·배포하는 방법을 README에 작성한다.
- 진료 상태는 `Asia/Seoul`, 요일별 시간, 점심·접수 마감, 날짜별 휴진·변경시간을 반영한다. ‘진료 일정 기준’임을 알리고 실제 접수·대기 상태와 구분한다.
- 휴일 데이터 관리 방법이 마련되지 않았거나 운영시간이 미확정이면 ‘진료 중’ 계산을 활성화하지 않고 확인된 시간표만 보여준다.
- 예약 URL·전화·주소가 없으면 작동하는 것처럼 보이는 더미 링크를 넣지 않는다. 초안은 미확정 상태로 처리하고 공개 전 값 확인을 필수로 한다.

### 후속 확장 제안

자가체크, 사전문진, EMR 연동, 문자 결과 발송, 자체 예약, AI 상담은 별도 단계로 둔다. 사용자가 원하면 문항·결과 안내·정보 처리와 운영 담당을 먼저 정한다. 초기 홈페이지에는 개인정보를 수집하는 자체 폼이 필요하지 않다.

원내 직원이 직접 자주 수정해야 한다면 CMS를 추가한다. 파일 기반 운영은 관리 화면이 없으므로 직원의 직접 편집 요구를 충족하는 것으로 설명하지 않는다.

## 6. 구현 구조 제안

**Next.js App Router + TypeScript + 정적 페이지 생성**을 권장한다. 공통 UI는 CSS 변수와 재사용 컴포넌트로 구성하고, 검색·메뉴·시간 상태처럼 필요한 부분만 클라이언트에서 처리한다. 구현 시점의 안정 버전과 잠금 파일을 사용한다.

자료의 아임웹·워드프레스 권장은 비개발자가 혼자 운영하는 상황을 전제로 한다. 이번 작업은 Sol이 구현하고 GitHub에서 변경을 관리하므로 코드 기반 구성이 적합하다고 판단했다. 다만 운영 인력과 수정 빈도는 확정해야 한다.

정적 export를 우선 검토한다. 동적 경로는 빌드 시 생성하고 이미지도 정적 배포 환경에 맞게 최적화한다. 서버 전용 기능이 필요해지면 배포 구성을 다시 결정한다. [Next.js 정적 export 공식 문서](https://nextjs.org/docs/app/guides/static-exports)

데이터를 화면에 직접 반복 작성하지 않는다.

| 데이터 | 관리 내용 |
| --- | --- |
| clinic | 이름, 주소, 대표자, 전화, 예약·지도 URL, 지역명 |
| schedule | 요일별 운영·점심·접수시간, 날짜별 예외, 갱신일 |
| doctors | 실제 경력, 진료분야, 사진 |
| care / examinations | 제공 분야, 승인된 설명, 관련 검사 |
| fees | 분류, 코드, 명칭, 비용 또는 범위, 포함 여부, 특이사항, 변경일 |
| notices / health / faq | 콘텐츠, 공개 여부, 날짜, 검토 상태 |
| assets | 원본 출처, 라이선스, 수정 내용 |

배포 업체·도메인은 미정이다. 호스팅 비용과 상업 이용 조건은 선택 시 확인한다. GitHub 푸시와 일반 공개 배포는 구분한다.

## 7. 원고·소재 반영 기준

진료 상세는 ‘이런 불편이 있나요 → 진료 시 확인하는 내용 → 검사·진료 과정 → 방문 전 안내 → FAQ → 예약’의 공통 형식을 사용한다. 의료 정보는 의료진 검토 후 공개한다.

원본 자료의 의료광고 관련 표는 검토 출발점으로만 사용한다. 특정 단어·사진·경력을 일괄 금지하는 자체 법률 규칙으로 구현하지 않는다. 확인된 사실과 실제 표현 맥락을 검토한다. 의료법 제56조는 치료 효과를 오인하게 할 우려가 있는 치료경험담, 거짓·과장 등의 광고를 제한한다. [국가법령정보센터 제56조](https://law.go.kr/LSW/lsLinkCommonInfo.do?chrClsCd=010202&lsJoLnkSeq=1028699907)

비급여는 제공된 HIRA 자료의 항목 구조를 참고해 접근 가능한 표와 검색 UI로 재구성한다. 예제의 다른 진료과 항목·금액은 복사하지 않는다. [HIRA 표준 웹페이지 서식 안내](https://www.hira.or.kr/cms/diag/01/npayform_02.pdf)

Servier 소재를 사용하면 제작자·원본 링크·CC BY 4.0 링크·변경 여부를 기록한다. [Servier 공식 라이선스 안내](https://smart.servier.com/)

## 8. 구현 순서와 완료 기준

1. **기초 설정·메인 시안:** 프로젝트, 디자인 변수, 공통 헤더·푸터·모바일 메뉴, 홈과 인터랙티브 인체 탐색. 모바일·데스크톱 화면을 비교해 디자인을 검토한다.
2. **정보 페이지:** 진료·의료진·검사·방문·FAQ, 공지·건강정보 템플릿, 비급여와 정책 페이지. 데이터 교체만으로 실제 의원 내용을 반영할 수 있게 한다.
3. **운영 연동:** 확정된 예약·전화·지도 링크, 운영시간, 예외일, 실제 콘텐츠를 연결한다.
4. **검증·푸시:** 빌드, 타입·린트, 주요 동작, 모바일 접근성 검증 후 GitHub에 커밋·푸시한다.
5. **공개 준비:** 의원 기본정보·콘텐츠·비급여·정책·도메인·호스팅을 확정하고 공개 배포한다.

완료 기준:

- 360 / 390 / 768 / 1440px에서 레이아웃과 한국어 줄바꿈 확인. 표 내부 외에는 가로 넘침 없음.
- 메뉴 열기·닫기·초점 복귀, FAQ, 예약·전화·길찾기 실제 동작.
- 비급여 검색·분류 조합과 빈 결과 확인. 금액을 hover 없이 읽을 수 있음.
- 시간 상태는 개시·종료·점심·요일 변경·휴진·특별진료 경계값 테스트.
- 키보드 탐색, 초점 표시, 본문 바로가기, 버튼 이름, 충분한 대비, 이미지 대체텍스트 적용.
- 개발 시연은 검색 노출을 막고, 공개 시 실제 주소 기준 canonical·sitemap·robots·메타데이터 설정.
- 실제 의원 정보를 기반으로 구조화 데이터 생성. 시간·연락처는 본문과 동일한 원천 데이터 사용.
- LCP 2.5초 이하, CLS 0.1 이하를 성능 목표로 설정. 출시 전 실험실 측정 조건과 결과 기록, 실사용 수치는 운영 후 확인.
- 예시 의원명·가격·사진·문구가 실제 정보로 오인될 상태로 공개되지 않음.

## 9. 확정이 필요한 정보

| 항목 | 현재 상태 | 필요한 시점 |
| --- | --- | --- |

| 중점 진료·실제 검사·장비 | 만성·알레르기 비염, 난청·이명 확정. 환자 표시명 암, 설명에 두경부 종양 병기. 장비 미제공 | 상세 원고 작성 전 |

| 시간·휴진·주소·주차·전화 | 미제공 | 운영 연동 전 |
| 예약·지도 URL | 네이버 예약 방식 확정, URL 미제공 | 운영 연동 전 |

정보가 미정이어도 공통 UI와 비공개 시안은 구현할 수 있다. 본 문서는 계획 제시 단계이며, 실제 코딩은 후속 Sol 작업에서 진행한다.

## 10. 상세 구현 명세

[화면 및 인터랙티브 인체 탐색 명세](interaction-and-screen-spec.md)를 함께 읽는다. 환자용 진료명, 홈 배치, 부위별 연결, 모바일·키보드 동작, 인수 조건을 정의한다. 인체 탐색은 초기 필수 기능이다.
