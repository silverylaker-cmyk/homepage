# 화면 및 인터랙티브 인체 탐색 명세

작성일: 2026-09-24. `website-plan.md`와 함께 Sol의 첫 구현 기준으로 사용한다.

## 1. 환자에게 보이는 진료명

| 구분 | 대표 표기 | 보조 설명 | 상세 경로 |
| --- | --- | --- | --- |
| 코 | 만성·알레르기 비염 | 코 진료 안내 | `/care/rhinitis` |
| 귀 | 난청·이명 | 귀 진료 안내 | `/care/hearing-tinnitus` |
| 암 | 암 | 머리·목 부위의 암과 종양(두경부 종양) | `/care/head-neck-cancer` |

사용자는 ‘두경부 종양’만으로는 환자가 이해하기 어렵기 때문에 **암이라는 말을 전면에 사용**하기를 요청했다. 메뉴·메인 진료 제목·탐색 결과 링크에서 ‘암’을 숨기지 않는다. 상세 페이지 H1은 **“머리·목의 암”**, 부제는 **“두경부 종양 진료 안내”**로 제안한다.

‘암’은 두경부 영역의 진료 안내 제목이다. 모든 신체 부위의 암 진료를 제공하는 것으로 확장하지 않는다. 종양이라는 단어가 등장할 때 모든 종양을 암과 동일하게 설명하지 않는다. 실제 검사·치료·수술·의뢰 방식은 자료 확보 후 작성한다.

## 2. 첫 화면과 섹션 구성

시각 방향: 따뜻한 아이보리, 먹색, 큰 한글 제목, 넓은 여백, 얇은 구분선. 그래픽은 짙은 선과 옅은 면 중심이며 선택 부위에 테라코타를 사용한다. 채도·그림자·움직임은 절제한다.

### 데스크톱

```text
알지 이비인후과     진료안내  병원소개  이용안내      네이버 예약
비급여 진료비 안내
──────────────────────────────────────────────────────────
신매역 · 알지 이비인후과

귀·코·목의 불편함,
충분히 듣고 설명하겠습니다.
만성·알레르기 비염 / 난청·이명 / 암
[진료 부위 살펴보기 ↓]  [네이버 예약]
──────────────────────────────────────────────────────────
어디가 불편하신가요?
그림이나 부위 이름을 선택해 진료 안내를 살펴보세요.

   머리·목 인체 그림                 선택한 부위 설명
   귀 / 코 / 입 / 목 표시            관련 진료 링크
   [귀] [코] [입] [목]               [자세히 보기]
──────────────────────────────────────────────────────────
01 만성·알레르기 비염                              자세히 →
02 난청·이명                                       자세히 →
03 암                       두경부 종양             자세히 →
──────────────────────────────────────────────────────────
진료철학 → 방문 안내 → FAQ → 푸터
```

위 문구는 시안용 제안이며 의원의 진료철학 확정에 따라 조정한다. 준비된 내용이 없는 병원소개·시간·사진·공지 항목은 빈 블록으로 나열하지 않는다. 초안의 메뉴에는 실제 확인 가능한 페이지 또는 섹션만 노출한다. 건강정보·검사·의료진·시설은 페이지 틀을 준비하고 실자료 확보 후 노출한다.

히어로는 데스크톱에서 약 520~680px 높이를 목표로 하되 고정 높이로 텍스트를 자르지 않는다. 인체 탐색 섹션은 첫 스크롤에서 발견할 수 있게 바로 다음에 배치한다. 3D 모델이나 회전 동작은 초기 구현에 필요하지 않다.

### 모바일

- 간결한 헤더 아래 의원명·주요 제목·진료 3개·탐색 버튼 순서.
- 인체 그림 → 부위 선택 버튼 → 선택 결과 순서로 한 열 구성.
- 그림 높이는 약 280~360px를 목표로 하며 작은 화면에서도 네 부위가 식별되어야 한다.
- 모바일 하단 고정 예약 버튼에는 safe area를 적용하고 본문에 여유 공간을 둔다.
- 상세 주소·전화가 없으면 임의의 값으로 전화·길찾기를 연결하지 않는다. 신매역은 지역 안내로만 표시한다.
- 실제 예약 URL이 없으면 ‘네이버 예약 준비 중’의 명확한 비활성 상태를 사용한다.

## 3. 인체 탐색의 범위

**머리부터 어깨까지의 2D 인체 일러스트**를 사용한다. 코·귀·입·목을 모두 구별할 수 있는 사선 또는 측면 구도로 제작한다. 전체 몸을 축소해 놓아 클릭 부위가 작아지는 구성을 피한다.

기본 도판은 repo에서 관리하는 SVG로 제작 가능하다. 제공된 Servier 해부도를 활용할 경우 실제 파일을 확인하고 출처·라이선스·수정 사항을 기록한다. 시각적으로 명확한 탐색 그림과 의학적 설명용 상세 해부도는 별도 소재로 사용할 수 있다.

| 선택 부위 | 그림의 위치 | 결과 패널 제목 | 연결 |
| --- | --- | --- | --- |
| 귀 | 보이는 귀 주변 | 귀 진료 | 난청·이명 → `/care/hearing-tinnitus` |
| 코 | 코 주변 | 코 진료 | 만성·알레르기 비염 → `/care/rhinitis` |
| 입 | 입 주변 | 입·목 부위 진료 | 암(두경부 종양) 안내 → `/care/head-neck-cancer` |
| 목 | 턱 아래 목 주변 | 목 부위 진료 | 암(두경부 종양) 안내 → `/care/head-neck-cancer` |

입·목 선택은 관련 안내를 찾는 탐색 동작이다. 클릭만으로 암 의심·위험도·검사 필요 여부를 판단하는 문구를 생성하지 않는다. 결과 패널 하단에는 짧게 **“부위 선택은 진료 안내를 찾기 위한 기능입니다.”**를 표시한다. 세 가지 진료 상세는 아래 텍스트 목록에서도 직접 접근 가능해야 한다.

## 4. 상호작용 상태

| 상태 / 입력 | 화면 반응 |
| --- | --- |
| 첫 진입 | 선택 없음. 그림과 4개 이름 표시. 패널에 ‘궁금한 부위를 선택해 주세요’ 및 세 진료 링크 표시 |
| 마우스 올림 | 부위 윤곽과 이름 강조. 결과 패널과 선택값은 바뀌지 않음 |
| 초점 이동 | 충분한 대비의 초점 표시. 선택값은 바뀌지 않음 |
| 클릭 / 터치 / Enter / Space | 한 부위 선택. 그림 강조, 버튼 상태, 패널 내용을 함께 변경 |
| 다른 부위 선택 | 이전 강조 해제, 새 패널 표시. URL이나 페이지를 자동으로 바꾸지 않음 |
| 같은 부위 재선택 | 현재 상태 유지 |
| ‘선택 초기화’ | 선택 없음 상태 복원 |
| ‘자세히 보기’ 클릭 | 해당 진료 상세 경로로 이동 |

결과 패널 높이는 데스크톱에서 최소 높이를 확보해 변화 시 화면이 튀지 않게 한다. 모바일은 패널을 바로 아래 두고 강제 스크롤이나 강제 초점 이동을 하지 않는다. 부위 버튼 바로 아래에 선택 결과 제목을 둬 터치 후 변화를 즉시 인지할 수 있게 한다.

전환은 150~220ms 색상·불투명도 변화 정도로 제한한다. `prefers-reduced-motion`에서는 즉시 전환한다. 지속적인 맥동, 자동 순환, 드래그·정밀 조작은 추가하지 않는다.

## 5. 접근성과 구현 구조

- SVG는 시각 표현을 담당하고, 부위 조작은 네이티브 HTML 버튼으로 구현한다. 그림 위 버튼과 아래 부위 버튼이 하나의 선택 상태를 공유한다.
- 각 버튼은 최소 44×44 CSS px 클릭 영역을 확보한다. 입과 코가 가까우면 연결선으로 라벨 위치를 벌려 터치 영역이 겹치지 않게 한다.
- 각 버튼에 ‘귀 선택’ 등의 이름과 `aria-pressed`, 결과 영역에 연결하는 `aria-controls`를 제공한다.
- 결과 변경은 짧은 `aria-live="polite"` 텍스트로 알리고 패널 전체를 매번 장황하게 낭독하지 않는다.
- 선택 여부는 색뿐 아니라 윤곽·텍스트로도 표현한다. 이미지 표현과 클릭 영역이 360px에서도 어긋나지 않아야 한다.
- 그림의 장식 경로는 보조기술에서 숨기고 전체 그림에는 적절한 설명을 제공한다. 같은 조작이 화면에 두 번 있으면 각각의 버튼 이름과 상태를 일관되게 유지한다.
- JavaScript가 비활성화되어도 세 진료 상세로 이동하는 일반 HTML 링크를 사용할 수 있게 한다. 비활성 버튼만 남는 화면을 피한다.
- 초기 상태는 서버·클라이언트에서 동일하게 렌더링한다. 선택 상태는 메모리에서만 관리하며 증상 입력·개인정보 저장 기능은 만들지 않는다.

제안 컴포넌트: `BodyExplorer`, `HeadNeckIllustration`, `RegionSelector`, `RegionPanel`. 실제 구조는 중복을 최소화하는 수준에서 조정 가능하다. 부위 데이터에는 `id`, `label`, 도판 내 상대 좌표, `panelTitle`, `links`를 두고 진료 데이터의 URL·명칭을 참조한다. 좌표는 그림의 동일한 비율 컨테이너 기준으로 계산한다.

## 6. 상세 페이지 공통 틀

1. 진료명과 쉬운 설명. 암 페이지는 ‘머리·목의 암’ 제목과 ‘두경부 종양’ 부제.
2. 의료진 검토 후 추가할 설명·상담 대상 원고 슬롯.
3. 확인된 검사·진료 과정만 노출하는 영역.
4. 관련 진료 안내 및 FAQ.
5. 네이버 예약. URL이 없으면 준비 중 표시.

초기 구현에서는 상세 페이지의 구조와 탐색 연결을 완성한다. 검토되지 않은 의학 원고를 대량 생성해 사실처럼 게시하지 않는다. 미확정 콘텐츠는 데이터의 공개 여부로 관리하고, 개발용 메모는 제품 본문에 섞지 않는다.

## 7. Sol 작업 순서와 검증

1. 홈 디자인과 인체 탐색을 첫 구현의 핵심으로 완성한다.
2. 클릭 결과가 연결될 진료 상세 3개를 구성한다.
3. 공통 정보 페이지·비급여 검색·콘텐츠 구조를 연결한다.
4. 로컬 실행 후 실제 브라우저에서 데스크톱·모바일 화면을 확인하고 스크린샷을 남긴다.
5. 빌드·타입·린트와 아래 핵심 상호작용을 확인한 뒤 커밋·푸시한다.

인체 탐색 인수 조건:

- 귀·코·입·목의 그림 버튼과 텍스트 버튼을 각각 조작할 수 있다.
- 선택·재선택·선택 전환·초기화가 명세대로 동작한다.
- 세 진료 경로가 존재하며 클릭한 부위에 맞는 안내로 연결된다.
- 입·목 선택 시 ‘암’이 보이되, 암이 의심된다고 자동 판단하는 문구가 없다.
- 키보드만으로 전 과정 사용 가능. 초점이 사라지거나 갇히지 않는다.
- 360 / 390 / 768 / 1440px에서 버튼 겹침·좌표 어긋남·가로 넘침이 없다.
- 모바일 터치로 hover 없이 모든 정보를 얻을 수 있다.
- 모션 감소 설정, JavaScript 비활성 상태의 상세 링크를 확인한다.
- 상호작용 테스트는 선택 상태·패널·링크의 실제 동작을 검증한다. 픽셀 좌표나 마크업을 그대로 복제하는 테스트는 쓰지 않는다.

이 명세까지 있으면 첫 구현을 시작할 수 있다. 다음 판단은 더 긴 문서가 아니라 실제 홈·인체 탐색 화면을 보고 내린다. 공개에 필요한 의료진 자료·비급여·운영시간·실제 예약 URL은 이후에 채운다.
